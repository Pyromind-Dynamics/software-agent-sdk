# 数据清洗任务的 LLM 网关密钥隔离：威胁模型与架构方案

状态：设计评审稿（未实施）
范围：`openhands-tools/openhands/tools/data_preparation/`（`df_run_pipeline` /
`df_submit_pipeline`）+ Pyromind 平台节点 + 数据清洗执行链路

---

## 0. 威胁模型（先对齐，这一版与初稿完全不同）

| | |
|---|---|
| **资产** | 平台的 LLM 网关密钥（长期有效、可跨任务复用、可直接计费外带） |
| **对手** | 提交数据清洗任务的**租户用户**。包括：能查看已提交任务/工作流定义的人，以及能进入执行节点的人 |
| **攻击面** | ① **提交任务** —— 节点定义 / 工作流 command / 任务 payload；② **节点** —— pod 运行时环境 |
| **目标** | 用户在以上两个面都无法取得密钥明文 |
| **非目标** | agent 手滑把明文写进脚本或会话事件（见 §7，那是另一个威胁模型） |

初稿把对手搞错了：它假设"泄漏来自我们的工具失误"，因此给了加密钥扫描、脱敏扩面
之类的方案。**那些方案全部作用于用户执行域内部，对"用户主动提取密钥"完全无效。**
下面重新推导。

---

## 1. 结论先行

**当前架构结构性无法满足目标**，因为密钥是被**设计成**注入用户可控执行域的，而不是
"某个环节忘了脱敏"。证据链见 §4。

只要密钥以任何形式（env / argv / 文件 / 挂载 / 内存）进入用户任务所能触及的执行域，
用户就必然能取得它。因此唯一的解法方向是：

> **让密钥根本不进入用户执行域** —— 引入平台侧的凭证代理（credential broker），
> 在**用户域之外**完成真实密钥的注入。

这不是加固，是架构改动。

---

## 2. 核心原理：为什么"在用户域内保护密钥"不可能

用户提交的 `pipeline.py` **就是在这个执行域里运行的代码**。这带来三条独立且都成立的
提取路径，堵住任何一条都不够：

1. **读环境**：`os.environ["DF_API_KEY"]`。一行代码。
2. **读进程**：`/proc/self/environ`、`ps auxww`、`/proc/1/cmdline` —— 即使 env 被清了，
   只要 key 曾出现在命令行里就还在。
3. **读提交的 command 字符串**：节点定义本身对用户可见（见 §4 证据 E3）。

**关键推论**：用户甚至不需要 shell。清洗脚本可以把密钥直接写进自己的产物：

```python
# 用户提交的 pipeline.py —— 平台会忠实地执行它
import os, json
with open(os.environ["DF_OUTPUT"], "a") as f:
    f.write(json.dumps({"leak": os.environ.get("DF_API_KEY")}) + "\n")
```

而 `processed.jsonl` 是用户可以正常读取的交付物。**任何"密钥在用户域内"的设计，
都等价于把密钥直接交付给用户。**

因此以下做法全部无效，无论实现得多精巧：

| 无效做法 | 为什么无效 |
|---|---|
| 加密后下发，节点内解密 | 节点能解密 = 明文；解密逻辑也在用户域内 |
| 藏在非常规 env 名 / 混淆 / 编译进镜像 | 可枚举、可提取，只是提高了一点门槛 |
| 只在任务启动瞬间注入，之后删除 | 进程内存与 `/proc/<pid>/environ` 仍可读；且用户代码全程在跑 |
| 降权 / 只读挂载 / 非 root | 用户代码与密钥同域，同 UID 即可读 |
| 在用户域内做日志脱敏 | 只防"顺手回显"，防不住主动读取（§4 证据 E5 正是这个误区） |
| 依赖"用户不会去看" | 不是控制措施 |

## 3. 目标架构

### 3.1 正解：网关代理 + 工作负载身份

```
用户 pod（无任何密钥）
   │  仅持有：代理地址 + 工作负载身份（SA token / mTLS）
   ▼
平台信任域的 LLM 代理            ← 真实网关密钥只存在于这里
   │  出口处注入 Authorization
   ▼
上游 LLM 网关
```

**要点**

- 用户 pod 里**不存在**任何形式的网关密钥。`DF_API_KEY` 要么不注入，要么注入一个
  任务级短期 token（§3.2）。
- 代理的调用方身份用**工作负载身份**（K8s ServiceAccount token、mTLS、服务网格
  NetworkPolicy），而不是共享静态密钥 —— 这样连"凭据"这个东西在用户域内都不存在。
- 代理侧按任务强制：**模型白名单 + QPS/额度配额 + 调用归属审计 + 可即时吊销**。
  用户即使滥用 pod 身份，也只能以该任务的身份调用白名单内的模型，额度受限且全程留痕。
- **代理必须是独立信任域**：不能是用户能 exec 进去的 sidecar（除非 sidecar 的身份
  与用户进程严格隔离且 sidecar 内无明文）。

**对 pipeline 侧零影响**：`pipeline.py` 照常读 `DF_API_KEY` / `DF_API_URL`，只是读到
的是任务 token 或空值。用户代码不需要改。

### 3.2 降级：per-task 短期 token

若代理暂时做不出来，退而求其次：

- 平台为每个任务签发 **TTL ≈ 任务时长**（分钟～小时级）的 token，绑定
  `task_id` + 模型白名单 + 额度上限。
- 网关侧校验该 token 并映射到真实密钥。
- 用户仍能读到这个 token —— **必须把这一点当成既定事实接受**，安全性来自
  "爆炸半径有限 + 可归因 + 可即时吊销"，而不是来自保密。
- 轮换成本必须足够低，否则吊销能力形同虚设。

这是过渡方案，不是终点：它把"永久密钥泄漏"降级为"限时限额的借用"，但用户依然
可以拿这个 token 做白名单内的免费调用。

### 3.3 配套：提交任务侧只留引用

- 工作流定义 / 节点 command 里只出现引用（`{{secret:llm-gateway}}` 之类），
  真值在平台侧解析，且**只在代理域内解析**。
- ⚠️ **常见陷阱**：`LookupSecret` / `{secret:KEY}` 这类引用机制如果解析后把值
  **注入用户 pod**，就等于没做 —— 只是把明文从 A 处搬到 B 处。引用必须与
  "值不落地到用户域"一起设计。
- 当前 EDP 链路正是这个陷阱的现成例子：profile 里写 `{secret:KEY}` 看着干净，
  但 `scripts/edp/sandbox_runner.py:1090-1096` 把真值经 `--set` 传进去后，照样落到
  沙箱 env 和 argv。

### 3.4 三者关系

| 层 | 作用 | 是否必需 |
|---|---|---|
| 3.1 代理 + 工作负载身份 | 让密钥不进入用户域 | **必需**（这是唯一真正的解） |
| 3.2 短期 token | 代理不可得时的降级；限制爆炸半径 | 过渡 |
| 3.3 提交物引用化 | 消除任务定义里的明文 | 必需（否则 §3.1 被绕过） |

## 4. 证据：当前实现把密钥放在了哪里

| # | 事实 | 位置 |
|---|---|---|
| E1 | 从会话 LLM 取出真密钥：`llm_api_key = llm.api_key.get_secret_value()` | `openhands-tools/openhands/tools/data_preparation/runner.py:355` |
| E2 | 密钥进入待注入 env 字典：`resolved[ENV_DF_API_KEY] = api_key`（回退链 `_nonempty_env(ENV_DF_API_KEY) or llm_api_key` 见 `:360`） | 同上 `:415` |
| E3 | **密钥被拼进节点 command 字符串**：`env_parts` 逐项 `f"{key}={shlex.quote(value)}"` → `env_prefix = " ".join(env_parts)` → `pipeline_step = f"{env_prefix} {venv_python} ..."`。这个 command 就是提交给平台的节点定义 | `openhands-tools/openhands/tools/data_preparation/platform_submit.py:1028-1038`、`:1051`、`:1069-1072` |
| E4 | 本地执行同样把密钥塞进子进程 env：`env.update(env_extra)` | `runner.py:522-526` |
| E5 | **脱敏只作用于日志回显**：`_redact_subprocess_output` 把子进程输出里的 key 替换掉 —— 但子进程**本身**依然持有明文 env | `runner.py:486-488`、`:547-559` |
| E6 | EDP 链路同构问题：`--set KEY=VALUE` 强制明文传值，值进 argv 与沙箱 env | `scripts/edp/sandbox_runner.py:1090-1096` |

**E3 是致命的一条**：密钥作为字符串出现在用户可见的节点定义里。用户不需要进节点，
看任务就能拿到。

**E5 是典型的范畴错误**：它在"让日志好看"这个层面做了正确的事，同时让"用户域内持有
明文"这件事原封不动。它给人的安全感恰恰是危险的 —— 看起来"已经脱敏了"。

## 5. 落地改造点

按依赖顺序：

1. **平台侧**（阻塞项）：LLM 代理服务 + 工作负载身份认证 + 按任务的模型白名单/配额/审计。
   这是前置条件，SDK 侧改造依赖它。
2. **切断 E3**：`platform_submit.py:1028-1038` 不再组装 `DF_API_KEY=<真值>`；改为只传
   代理地址 + 任务身份，或什么都不传（靠网络身份）。
3. **切断 E2/E4**：`runner.py:410-415` 不再把真密钥放进 `resolved`；本地执行路径
   (`:522-526`) 同样。
4. **切断 E6**：`sandbox_runner.py` 的 `--set KEY=VALUE` 改为 `--secret-from-env KEY`
   （从平台侧注入的进程环境读），或改由代理承担。
5. **提交物引用化**：workflow 定义 / profile / manifest 中只留引用，且确认平台
   不会把解析后的值回显到用户可见的任务定义里。
6. **清理历史**：已提交任务定义与产物中可能已含明文。密钥轮换是必须的；是否需要
   清理介质见 §8。

## 6. 验收标准：红队测试

**必须以攻击者视角验收**，而不是检查代码里有没有关键词。以下用例用户主动尝试
提取，**全部必须失败**：

1. 在 `pipeline.py` 中 `print(json.dumps(dict(os.environ)))` 并把结果写进
   `processed.jsonl` → 输出中无网关密钥。
2. 节点内 `cat /proc/self/environ`、`cat /proc/1/cmdline`、`ps auxww`、
   `env | grep -i -E 'key|token|secret'` → 无网关密钥（只有任务 token 或空）。
3. 查看已提交的 workflow 定义 / 节点 command / 任务 payload → 无网关密钥。
4. 枚举 pod 内挂载（K8s Secret、SA token、挂载卷）→ 无网关密钥；若用了 SA token，
   确认其权限仅限该任务且无法换取长期凭据。
5. 用提取到的任何凭据（若有）在任务外调用网关 → 被拒（白名单/配额/吊销生效）。

## 7. 与"agent 手滑泄漏"的关系（初稿 A–E 方案的定位）

初稿针对的是另一个威胁模型：**agent 在生成脚本、下发指令时把明文写进会话事件**。
那套方案（门禁扫描、runner `--secret-from-env`、脱敏扩面、`LookupSecret` 引用化）
在**那个**威胁模型下是有效的，可以作为纵深防御保留。

但必须明确两点：

- 它们**不能**满足本方案 §0 的目标。理由：它们全部发生在用户执行域**内部或上游**，
  而对手就在那个域里。用户域内持有明文这一前提不变，用户就能拿到。
- 其中"脱敏扩面"（初稿 D 层）如果被当成主方案会很危险 —— 它与 §4 E5 是同一类
  范畴错误：让日志干净，却不改变密钥可被读取的事实。

建议：把初稿的 A/B 作为**卫生措施**（减少意外扩散、缩小需要清理的历史面），
但不要把它们当作本目标的交付物。

## 8. 开放问题

1. **平台是否已有 LLM 代理 / egress gateway？** `df_run_pipeline` 走的
   `DF_API_URL`（`runner.py:303` 校验为 OpenAI-compatible chat completions endpoint）
   目前指向哪里，是直连上游网关还是已有一个中间层？这决定 §3.1 是改造还是新建。
2. **是否具备工作负载身份？** K8s ServiceAccount token / mTLS / 服务网格其一即可。
   若只有静态共享凭据，§3.1 的"无凭据"形态无法达成，只能落到 §3.2。
3. **网关是否支持子 token 签发与配额？** TTL 下限、模型白名单粒度、配额维度、
   吊销延迟 —— 决定 §3.2 能收敛到什么程度。
4. **平台会向用户回显多少任务定义？** 用户能否看到节点 command、env、挂载配置。
   这决定 E3 的实际暴露面（如果是命令字符串，暴露面就是 100%）。
5. **DataFlow 侧是否需要改动？** `pipeline.py` 读取 `DF_API_KEY` 的约定可以保留
   （代理模式下读到 token 或空），但要确认 open-dataflow 的
   `APILLMServing_request(key_name_of_api_key=...)` 是否强制要求非空 key —— 若强制，
   代理模式需要它接受"无 key 但有网络身份"的调用方式。
6. **历史清理范围？** 已提交的任务定义（含 E3 的 command 字符串）与已产出数据中
   可能已含明文。仅轮换密钥，还是需要清理平台侧的任务定义与产物？
