# 测试 / 调试 Pyromind 工作流

边界：请求同时要求修改配置与“跑一下/看看效果”时，先用 `generate-workflow-dsl` 完成 DSL 修改，
本轮停止；不要调用 `workflow_debug`。本 Skill 只接收不含配置修改的显式测试/调试请求。

## 能力边界

| 工具 | 作用 | 何时使用 |
|------|------|----------|
| `validate_workflow_dsl` | 检查 DSL 结构 | 每次写入或修改后 |
| `workflow_debug` | 真实试跑并返回异步终态 | 用户明确要求测试、调试或试跑 |
| `run_workflow` | 发布或执行生产工作流 | 用户明确要求正式运行或发布 |

## 前置条件

- 工作区已有 `public_data/workflow_canvas/workflow.py`；否则先生成。
- 若本轮刚改过且未校验，先调用 `validate_workflow_dsl`，通过后再测试。

## 循环步骤

1. 调用 `workflow_debug(dsl_path="public_data/workflow_canvas/workflow.py")` 提交当前工作流。
2. 提交失败：按错误语义处理，不盲目重试。
3. 提交成功：告知用户已提交、正在等待平台结果；等待异步终态。
4. 收到终态后：

   | 终态 | 下一步 |
   |------|--------|
   | **Succeeded** | 仅简短告知用户本次测试成功，然后停止并等待后续输入；不要重复调用 `workflow_debug`，也不要主动继续改 DSL |
   | **Failed / Error** | 根据错误信息重新生成或局部修复工作流，调用 `validate_workflow_dsl` 后再次调用 `workflow_debug` |
   | Terminated | 向用户说明；按 `error_log` 决定是否修复后再测 |
   | Pending / Running | 仍在跑；等待 callback，勿重复提交同一轮 |

5. 达到平台给出的最大尝试次数后，如实告知用户并停止。

## 失败时如何改 DSL

- 仔细读错误信息，对照对应节点契约。
- 优先按报错修复或**按错误语义重生成相关节点/整份 DSL**（use.md：可能需要重新生成）
- 改完校验通过后必须再次测试，形成闭环。
- 同一报错连续两轮无进展时，重读文档后再换修法，不要机械重复同一修改

## 成功时如何沟通

- 测试任务成功时只提示一句「本次测试工作流成功」，然后等待用户下一步指示。
- 正式运行任务按通用会话指引继续，不套用测试任务的等待规则。

## 与用户的沟通（进行中）

- 提交后：说明已提交并等待平台结果
- 失败修复循环中：一两句进展即可，不必整段粘贴 `error_log`
- 仅在达最大次数或明显是平台资源/权限问题时再向用户确认下一步
