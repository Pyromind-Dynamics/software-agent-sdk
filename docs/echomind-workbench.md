# EchoMind 当前工作台链路

当前入口是“对话准备 → 审阅 workflowPLAN → 创建并启动 Project → 阶段工作台”。
不再使用旧实验计划版本面板、SQL 后台工作队列面板或旧 baseline 验收客户端。

## 准备与执行

- 创建 Project 前，Manager 根据 preparation policy 收集事实、探查资源并生成计划。
- 用户通过创建按钮确认当前 preparation revision；Runtime 创建 Project，
  激活开发工具策略并通知 Manager。
- 主 Agent 按获批计划直接执行研发阶段，依次登记数据、模型和评测报告。
- Runtime 按计划任务与执行次数关联平台回调；运行中追加的需求可在当前回合结束后出队。
- 场景差异只在 Profile、Prompt 和场景 Skill 中，前端不根据角色硬编码业务逻辑。

## 从研发成果生成执行方案

在开发态 Project 跑完 Dataset、Train、Eval 后，打开「调试与发布」，点击「生成并验证执行方案」。
工作台会选取本会话的成功研发任务。同一阶段有多个成功版本时，可以在「指定研发任务 ID」中选择。
工作台显示每个阶段的资产来源和验证方式，主 Agent 根据缺口补齐对应步骤。
需要决定标签来源或验证集时，在会话里回答，工作台会继续检查。

Dataset 用同一套准备、处理和导出脚本在不同输入上回放，检查样本身份、训练行、媒体和验证集。
Train 与 Eval 显示工作流绑定的静态校验结果，正式执行仍可在后续调试中验证。
核对标签由哪一侧提供、训练中验证集的取法以及实际覆盖的输入形式，再点「确认采用」。
主 Agent 在计划内记录下游所需的已验证产物，长脚本、版本和正式评测报告按引用保留。

## 状态与前端

主对话展示研发执行，阶段栏按任务展示平台状态、历次执行和报告。平台成功后，主 Agent 核对产物并记录业务结论。处于运行或等待回调的历史子任务安全结束后再迁移，已有记录可查看。

## 保留的兼容边界

当前 preparation / Project 仍复用 `domain/experiment_plans.py` 中的工作流模型。
该模块名不意味着旧实验计划执行链仍在使用。

公开 Snapshot 的旧可选字段与已有数据库迁移链保留，以免破坏其他客户端、
已有部署或持久化解析。删除本地历史会话不等于这些外部契约已全部退役。
本次清理不重置数据库、不删除迁移、不改变公开协议版本。

## 发布后的批次、报告与人工上线

“调试与发布”工作台包含三个 Project 级面板：持续批次调度、模型与评测报告、
模型部署与回滚。研发阶段确认并冻结评测规则，运行阶段使用已发布版本执行；
每轮完成后归档候选模型和 Eval 结果，由用户决定是否部署，不自动晋升模型。

持续调度默认关闭。开启前需要完成资源搭建、Tracer 批次管理授权，以及后台
Storage 访问。Storage 可显式绑定同账号、同集群且挂载 `/workspace` 的运行中
Sandbox。绑定不保存浏览器 Cookie；实例停止或删除后显示阻塞，不自动替换实例。
Tracer 的 `/admin/batches` 接口使用 `ADMIN_API_KEY`；它与代理采集凭据是不同配置项，
部署时可以设置成相同值，但不能假设平台返回的 `secret_key` 已获得批次管理权限。

持续调度按批次顺序领取封批数据，串行执行 Dataset → Train → Eval。
成功且评测报告已验证、归档后才释放 Tracer 中的已消费批次。
训练使用已确认标签，不把模型预测直接当成 GT；失败或提交结果不确定时保留数据，
工作台展示具体原因和对应运行。停止调度不再接收新批次，已经提交的任务继续收尾。

标注清单和固定验证集使用 JSONL。每行包含 `id`、`confirmed: true`、`user_prompt`、
`images`（`/workspace` 下的绝对图片路径）和 `gt`（字符串或结构化标签）；
训练清单还必须提供与 Tracer 采集对应的 `task_id`。两份数据的样本 ID 和图片应互不重叠。
Agent 在新 Project 的数据准备阶段生成这些清单，用户确认标签和划分后再开启调度。

报告列表读取本轮 Eval 的指标、评分维度、权重、阈值及数据与规则指纹，
不另加一套分数。仅相同评测口径的报告可排名和对比；缺少指纹仍可查看实际指标，
但不参与比较。原始 HTML 概览在隔离环境预览，样本、GT、模型输出和图片通过
候选模型绑定的分页接口读取。样本通过阈值不代表模型上线门槛。

用户选择候选并确认后，系统创建候选 Inference，等待就绪，更新 Tracer 上游，
验证实际响应来自目标模型后才更新线上记录。平台更新可能短暂重启 Tracer。
旧 Inference 保留用于回滚并继续占用资源；部署失败的候选资源在确认不承载流量后清理。
后台只恢复已经授权的部署，不自动挑选新模型。

## 标准 Project 的验收顺序

1. 准备真实图片和已确认标注，单独冻结验证集；确认漏检、误检等业务指标及统计方式。
2. 研发并调试 Dataset、Train、Eval，核验图片到训练数据的转换、模型产物和逐样本评分。
3. 搭建 Inference 与 Tracer，完成少量真实图片采集验收，再发布已验证的 Project。
4. 配置标注清单、固定验证集、后台 Storage 与批次管理授权，开启持续调度。
5. 连续产生两个新批次，核对各批只运行一次、报告真实归档、批次释放、线上模型保持不变。
6. 人工选择一个候选部署，核对实际流量和线上标记；执行回滚，再次核对模型身份。

自动晋升是后续独立策略：可以复用这些报告和部署接口，不改变研发阶段冻结的评分规则。

## 回归验证

```sh
uv run pytest tests/pyromind_runtime
```

在 `minimal-chat-frontend` 中运行 `npm test`、`npm run lint` 和 `npm run build`。
实际平台验收通过当前工作台进行，核对主会话的待执行任务、平台任务 ID、状态回调、报告和续跑上下文。

Sandbox SDK 的目录检查使用 TLS WebSocket。若本地 Python 缺少系统 CA，需在启动
服务进程前配置可信证书，例如 `SSL_CERT_FILE` 指向 `certifi.where()` 返回的文件，
然后重启服务。不要关闭 TLS 校验；在已经导入 aiohttp 的进程里临时设置该变量
不能保证生效。Storage 绑定验证会将这类连接失败显示为 blocked。
